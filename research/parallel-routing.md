# 2단계 의미 라우팅: 수식과 실제 검증

`notebook/07_mathematical_framework.ipynb` 10~14절과 `config/parallel_routing.json`을 사용한다.
이는 새로운 검색 정책의 첫 제한된 실험이며, 정확도·상수 시간·기존 RAG 대비 우위를 미리 가정하지 않는다.

## 준비와 온라인 정책

1. 공통 원문을 기존 Jev 분류 경로, 제목, ID 순서로 정렬해 최대 g개씩 나눈다. 중복 배치가 있었던 원문도 새 묶음에서는 한 번만 포함한다.
2. 원문 전체만으로 주제 설명·원문 개체명·원문 인용 Q&A를 공통 생성기가 만든다. 질문·정답 라벨은 준비 입력에 없다. 개체 최대 12개, Q&A 최대 2개를 적용하며 초과/원문 미확인 항목과 API의 JSON 외 설명문 처리는 기록한다. 원시 응답은 유지한다. 요약의 모든 문장을 사실 검증했다는 뜻은 아니다.
3. 모든 묶음 설명을 Noul로 판단하고 상위 r개를 선택한다. 그 안의 모든 원문을 Score로 판단해 최대 k개의 원문을 반환한다. 초기 k=5, 공통 근거 텍스트 예산 2,000토큰이며 예산 제외 원문 ID도 저장한다.
4. 동일 GPT-6 Luna 프롬프트·설정으로 답변을 생성하고 동일 근거·답변 평가기로 평가한다. C-parallel은 원격 Jev, D-parallel은 pinned local Laya다. 기존 C/D 트리 방식은 보존한다.

이 첫 실험은 기존 Jev 분류·사람이 만든 분류체계를 상속한다. 분류 적재 자체를 새 알고리즘으로 대체했다고 쓰면 안 된다.
그룹 경계는 카테고리 경계를 넘을 수 있으며 설명은 원문 정보를 모두 보존하지 않는다.

## 수식의 적용 범위

균등 그룹과 고정된 r, 동일 단가라면 판단 횟수는

$$W(g)=\lceil N/g\rceil+\sum_{i\in S_q}|G_i|\leq\lceil N/g\rceil+rg.$$

그룹과 원문 판단의 평균 입력량 a,b를 상수로 근사할 때

$$U(g)\approx aN/g+brg,\qquad g^*=\sqrt{aN/(br)}.$$

실제로 a,b는 설명 길이·질문·프롬프트·패킹·선택 원문에 따라 변한다. 개발 로그에서 측정한 a,b로
고정한 정책의 새 평가 입력량을 예측하고 실제 사용량과 대조한다. 같은 개발 관측에 식을 맞춘 것만으로 검증을 선언하지 않는다.
고정 g에서는 W가 N에 선형이며, 고정 하드웨어에서 두 논리 단계는 일정한 경과 시간을 뜻하지 않는다.

단계 s의 실제 벽시계 시간을 T_s로 측정한다. Jev는 제한된 동시 HTTP 요청을 사용하고 물리적 시도마다 사용량을 한 번만 센다.
Laya는 같은 단계의 독립 상태를 GPU 배치로 처리하며 예정 배치 수와 추론 시간을 따로 기록한다.
예정 배치 수는 SDK 호출 인자에서 계산한 값으로, forward hook으로 직접 센 실행 횟수는 아니다.

$$T_{retrieval}=T_{macro,wall}+T_{micro,wall}+T_{기타},\qquad
C_{API}=C_{판단API}+C_{생성API}.$$

로컬 GPU의 금전 비용은 미측정이다. 자료 적재 비용은 기존 분류 비용과 새 설명 생성 비용을 각각 보존하며,
Q개의 질문에 대해 준비 비용을 상각한다면 별도의 $C_{prep}/Q$ 항을 둬야 한다.

## 품질과 데이터 분리

정답 annotation의 모든 근거 그룹을 확보한 사건 H와 전달 원문이 완전 근거를 포함한 사건 E를 구분한다.

$$R_{evidence}=P(H)P(E\mid H).$$

원문 집합이 묶음 후보의 부분집합이므로 이 실험에서는 E가 H를 함의한다. 여러 annotation은 대안으로 허용하며
HotpotQA에서 관련 그룹 하나만 발견한 것은 H 성공이 아니다. 0건의 조건부 분모는 미정으로 남긴다.
그룹 TPR/FPR은 모든 유효 annotation의 근거가 있는 그룹의 합집합을 양성으로 정의한다.

개발에서 r 최댓값까지 모델을 실제 실행한 뒤 작은 r의 품질은 재생한다. 재생한 품질 결과에는 실제 지연·사용량·API 비용을 붙이지 않는다.
설정 선택은 B의 개발 완전 근거 확보율을 충족하는 설정 중 입력량 proxy가 작은 것을 우선한다.
목표를 충족한 설정이 없으면 개발 근거 확보율을 우선하고 실패를 명시한다. proxy는 청구 토큰이나 연산량이 아니다.

정책·모델·그룹 해시를 먼저 고정하고 이전 실험에서 평가한 질문 ID를 제외한다. 이후 평가 라벨을 읽는다.
동일한 새 질문에서 A/B와 두 새 방법을 매번 직접 실행하며 방법 순서를 무작위화한다.
정답 근거를 강제로 포함한 2,000문단 축소 corpus, 작은 질문 표본과 반복 1회라는 범위를 유지한다.

## 기록과 재실행

- `data/parallel_groups/<hash>/`: 원문 참조·설명·압축 제외 항목·준비 요청/응답·비용·완료 해시.
- `results/parallel_*/development_judgments.jsonl`: 실제 개발 macro/micro 점수·입력·usage·시간·단계별 호출.
- `development_quality.jsonl`, `development_questions.csv`, `development_summary.csv`: 재생한 설정별 품질과 TPR/FPR.
- `frozen_policy.json`, `policy_before_eval_labels.json`: 선택 규칙·정책·모델·해시와 평가 라벨 로드 전 기록.
- `system.jsonl`, `questions.csv`, `summary.csv`: 새 문항의 실제 검색·생성·근거·EM/F1·API 비용.
- `decision_calls.jsonl`, `results/raw/`: 물리 요청/응답, 실제 로컬 상태·토큰 ID·출력·입력 잘림 검사. 인증 정보는 제외.
- `analysis/`: 개발 품질/입력 proxy 그림, 실제 비교 그림, 단계 프로파일과 새 평가 입력량 예측 오차.

07의 기본 읽기 모드는 결과 해시·질문 집합·근거/답변 지표·생성 비용·요약 표와 정책 고정 해시를 다시 검사한다.
유료 실행은 10절의 스위치를 켰을 때만 시작하며 SDK 자동 재시도는 없다. 설정된 물리 API 호출 한도를 초과하면 중단한다.
형식 오류나 입력 예산 위반 시 부분 결과를 남기며 사실을 임의로 보정하거나 원문을 잘라 진행하지 않는다.
설명 생성의 출력 한도에 걸렸더라도 필요한 JSON 객체가 하나의 완결된 형태로 반환됐으면 이를 검증해 사용하고,
출력 미완료 상태와 JSON 밖에서 제외한 설명문을 기록한다. 입력 원문 잘림을 허용하는 규칙은 아니다.
준비 체크포인트는 준비 설정·원문 ID·내용 해시·원문 인용 검증이 일치할 때 재사용하며, 재사용 비용과 이번 세션의 새 호출 수를 구분한다.

작은 표본의 EM 순서가 일반적인 정확도 순서라는 뜻은 아니다. 이전 트리 실험은 질문이 달라 직접 개선율을 계산하지 않는다.

Jev는 필요한 근거가 후보 묶음 안에 모두 들어 있는 비율 75%, 그 조건에서 최종 근거를 모두 전달한 비율 100%였다.
따라서 이번 Jev 실행의 근거 누락은 묶음 선택에서 발생했다. 요약 손실·묶음 구성·판단 프롬프트·모델 판단 중 어느 것이 원인인지는 이 값만으로 확정할 수 없다.

개발 로그로 측정한 Jev a=329.456,b=321.19075를 고정한 입력량 식은 새 평가에서 65,064.675토큰을 예측했고,
실제 평균은 65,161.4토큰이었다(상대 오차 약 -0.15%). 같은 가정의 정지점 g는 약 20.3이다.
Laya의 입력 예측 오차는 약 -0.64%였다. 이는 해당 설정의 입력량 모형 검산이며, 회수율·지연·전체 운영비 최적성의 증명이 아니다.
Jev의 두 논리 단계는 실제 HTTP 요청 평균 8회였고, Laya는 예정 로컬 배치 평균 24개였다. 입력 잘림은 모두 0건이었다.

독립 검산 기록은 `analysis/validation_checks.json`에 저장했다. 80개 관측의 원문 참조,
20문항의 A/B 동일 후보·동일 dense 점수, 이전 평가 ID와 중복 없음, 981개 고유 물리 API 시도,
공급자 원시 청구 기록과 질문별 비용의 일치를 확인했다. 모델 품질이나 통계적 유의성까지 보장하는 검사는 아니다.
설명 준비 누적 비용은 g=20 약 $0.050918,g=50 약 $0.042415이며, 상속한 Jev 분류 준비 비용 약 $0.081653은 별도다.
이 값은 실패한 개발 시도의 모든 청구액을 포함한 연구 총지출이 아니다.

## 후속 개발: 대표 설명 길이

07의 15~18절에서 공통 corpus·그룹 소속을 유지하고 Jev g=20,K=5,k=5를 고정한다.
180·360·720토큰을 목표로 같은 준비 프롬프트를 적용한다. 기존 '짧게' 프롬프트의 결과를 섞지 않도록
세 조건 모두 새로운 준비 프로토콜을 사용한다. 포맷(요약·개체명 최대 12개·원문 인용 Q&A 최대 2개)과
공급자 출력 상한을 같게 두고 목표 분량만 바꾼다. 길이는 정규화 후 설명 JSON의 o200k_base proxy로 확인한다.
목표 길이와 실제 길이가 다르면 실제 분포·목표 80~120% 범위 안의 비율을 남기며, 잘라 맞추지 않는다.

개발 40문항에서 조건 순서를 무작위화해 세 조건의 검색을 각각 새로 실행한다. 묶음 확보율과 최종 완전 근거 확보율,
물리 요청·공급자 청구 입력·요금·실제 단계/전체 시간을 기록한다. 같은 질문의 성공/실패 변화도 대조한다.
B의 개발 목표 87.5%를 충족한 관측 조건 안에서만 판단 API 비용의 최저값을 비교하며, 충족한 조건이 없으면 실패를 명시한다.
평가 라벨·최종 답변 생성기를 사용하지 않으므로 답변 EM·서비스 전체 비용·일반화 성능을 검증한 결과가 아니다.

실행 설정은 `config/representation_length.json`, 구현은 `rag_baselines/representation_length.py`다.
`results/length_*/`에 고정 조건·개발 근거 라벨·준비 영수증·질문별 원시 결과·완료 해시를 보존한다.
실제 HTTP 원시 로그는 각 manifest의 `raw_log` 경로에 연결되며, 청구액을 질문별 결과와 대조한다.
설명 준비만 체크포인트를 재사용할 수 있고, 실제 검색 시간은 새 호출에서 측정한다.

470.956/593.390/747.688토큰, 원문 판단당 b는 약 321토큰이었다. 실제 질문당 입력량은
79,212.35/91,403.30/106,857.875토큰으로 기록돼 100a+100b 분해와 일치한다.
이는 같은 실행의 회계 분해이며 새로운 표본의 예측을 검증한 것은 아니다. 제약을 충족한 관측 후보가 하나여서
전체 길이 공간이나 실제 서비스 운영비의 최적값을 찾았다고 해석하지 않는다.

실제 길이는 목표와 달랐다. 목표의 80~120% 안에 든 그룹 비율은 0%/60%/43%였으며 조건별 길이 분포도 겹친다.
따라서 정확히 180·360·720토큰을 통제한 실험이 아니라, 같은 준비 프로토콜의 목표 분량을 바꾼 실험이다.
이전 '짧게' 프롬프트의 개발 60%는 준비 조건이 달라 직접적인 길이 효과 계산에 섞지 않는다.

실제 HTTP 시도는 OpenAI 설명 준비 300회, Jev 검색 1,120회이며 모두 HTTP 200이었다.
설정 단가와 usage로 계산한 이번 세션의 준비 비용은 약 $0.204425, 판단 비용은 약 $0.466156이다.
최종 답변 생성·로컬 GPU·상속한 기존 분류 준비 비용은 이 합계에 포함하지 않는다. 공급자 청구서 대조 금액은 아니다.
질문/요약 CSV·원문 근거·그룹 소속·고정 정책·usage·물리 비용·요청/응답 본문 해시를 검산한다.
공급자 응답에 기록된 입력 잘림은 0건이며 클라이언트의 byte 한도도 준수했다. 공급자 내부의 모든 처리를 직접 관찰한 뜻은 아니다.
개발 탐색 결과이므로 답변 EM이나 일반화 성능·통계적 우위를 주장하지 않는다.

## 08: 선택한 길이 조건의 실제 답변 비교

개발에서 목표를 충족한 관측 조건인 720 목표 설명을 그대로 재사용한다. 재요약·추가 튜닝 없이
g=20,K=5,최종 근거 최대 5개를 고정한다. A/B 모델·리비전·검색 50개·공통 생성기도 유지한다.
D는 C와 같은 설명·정책으로 Laya를 실행하는 전이 비교이며 D의 최적 정책이라는 뜻은 아니다.

`config/frozen_comparison.json`의 `questions_per_task`는 각 데이터셋의 새 평가 문항 수다.
과거 평가와 개발 ID를 제외하고, 정책·질문을 기록한 뒤 평가 라벨을 로드한다.
모든 방법을 준비·warm-up한 뒤 같은 문항에서 순서를 섞어 실제 검색과 GPT 답변 생성을 실행한다.
warm-up 판단 API 비용은 별도로 보존하고, 온라인 지연에는 진단 로그 수집 시간을 포함한다.

`notebook/08_compare_frozen_routing.ipynb`는 답변 EM/F1·완전 근거 확보율·전체 시간·실제 GPT 입력·온라인 API 비용을
분리해 시각화한다. 기본 실행은 마지막 완료 결과를 재검증하며 유료 호출을 하지 않는다.
출처는 `results/frozen_*/system.jsonl`·`questions.csv`·`frozen_policy.json`과 manifest의 `raw_log`다.
개발 92.5%를 새 평가의 답변 정확도로 바꾸어 표기하지 않고, 과거 07의 다른 문항과 인과 개선율을 계산하지 않는다.
