# BERGEN 기반 RAG와 Jev 직접 근거 선택의 비교 연구 계획

작성일: 2026-10-03, 한국 시간. 아래 본문은 구현 전 연구 설계 기록이다.

**구현 업데이트:** A/B/C/D adapter와 공통 데이터 준비·평가·계측을 구현했다. 현재 실행 기준은 [README](../README.md), [공통 규격](baseline-contract.md), [C 구현 규칙](c-method.md)을 따른다. NQ와 다중 자료 질문용 HotpotQA를 사용한다. C는 원격 Jev, D는 로컬 Laya로 판단하지만 같은 Jev-prepared tree를 쓴다. 아래 C의 Choice/tournament와 고정 선택 수는 과거 설계다. 현재 트리 경로는 독립 분기 판단·가변 근거 수를 사용한다.

**BERGEN의 공개 RAG 구성과 KILT 데이터셋을 기반으로, 같은 상용 LLM API 앞에 RAG 또는 Jev를 연결하여 최종 답변 정확도·전체 응답 시간·토큰 및 총비용을 비교한다.**

이 문서의 본문 수치는 당시 실험 설정과 계획이다. 현재 실행 결과와 제한은 위 구현 문서에 기록한다. 소규모 API 연결 검증을 전체 benchmark 성능 재현으로 해석하지 않는다.

구현도: [decision_LLM · RAG vs Jev 연구 아키텍처 (FigJam)](https://www.figma.com/board/y0vkst2DLqMq14w9sRsqkZ). 기본 RAG, 재정렬 RAG, Jev 직접 선택의 자료 준비·온라인 흐름과 원본 코드 링크를 담았다. A/B는 아래 고정 BERGEN 코드·설정을 기반으로 재구성했으며, 공통 상용 생성 API와 C의 선택 정책은 우리의 연구 구성이다.

## 1. 이번 연구에서 사용할 구성

| 항목 | 채택한 구성 |
|---|---|
| 실험 기반 | BERGEN: 공개 코드·검색/재정렬 설정·QA 평가 기능 |
| 첫 과제 | 영어 문서 기반 질문 답변: KILT Natural Questions |
| 공통 자료 | KILT Wikipedia를 BERGEN KILT100w 방식으로 분할한 동일 passage 집합 |
| A: 기본 RAG | RetroMAE 벡터 검색 → 상위 5개 근거 → 공통 LLM API |
| B: 재정렬 RAG | 같은 RetroMAE의 상위 50개 → DeBERTa-v3 재정렬 → 상위 5개 → 공통 LLM API |
| C: Jev 직접 선택 | 공통 자료 전체를 Jev로 판단 → 상위 5개 근거 → 공통 LLM API |
| 핵심 결과 | 최종 답변 정확도, 질문당 전체 응답 시간, 단계별 토큰과 총비용 |
| 첫 실행 | 개발용 100문항으로 연결·계측 점검 후, 별도 평가 500문항을 규모별 비교 |
| 초기 범위 | 텍스트, 사전 학습 모델 사용, 추가 파인튜닝 없이 비교 |

A와 C가 주 비교다. B는 검색 이후 재정렬을 추가한 기준으로, Jev의 효과를 단순한 검색 개선과 비교하는 데 사용한다. A/B에서 쓰는 모델과 후보 수의 출처는 §4에 고정한다.

**C는 벡터 검색이나 BM25가 미리 고른 후보에만 Jev를 적용하는 방식으로 바꾸지 않는다.** 규모별 공통 corpus 전체가 C의 첫 판단 대상이다. Jev 내부에서 여러 창과 단계로 후보를 줄이는 과정은 C의 알고리즘이며, 그 시간·호출·사용량을 모두 포함한다.

## 2. 연구 질문과 가설

연구 질문은 다음과 같다.

> 같은 자료, 질문, 근거 예산, 최종 상용 LLM을 사용할 때, Jev의 직접 근거 선택은 RAG보다 정확도·속도·비용에서 어떤 이점과 한계를 보이며, 자료 규모에 따라 그 관계가 어떻게 달라지는가?

| 가설 | 검증할 결과 |
|---|---|
| H1: 정확도 | C의 최종 답변 EM/F1이 A 또는 B보다 높을 수 있다 |
| H2: 속도 | C의 질문 수신부터 답변 완료까지 시간이 A 또는 B보다 짧을 수 있다 |
| H3: 비용 | C의 선택 단계와 최종 생성 단계를 합친 질문당 비용이 A 또는 B보다 낮을 수 있다 |

세 축을 동등하게 다룬다. 정확하지만 느리거나, 빠르지만 비싸거나, 모든 축에서 불리한 결과도 그대로 보고한다. 세 결과를 임의의 가중치로 합쳐 단일 승자를 만들지 않는다.

자료 규모는 별도의 성능 지표가 아니라 실험 조건이다. **같은 질문을 유지하면서 자료를 늘렸을 때 세 핵심 결과가 어떻게 변하는지** 측정한다.

첫 결과의 적용 범위는 영어 Wikipedia 기반 단답형 QA다. 회사 내부 자료, 한국어, 이미지, 다중 근거 질문에 대한 주장은 해당 조건을 실제로 평가한 뒤 추가한다.

## 3. BERGEN과 KILT를 사용하는 이유

| 자료 | 역할 | 이번 연구에서 채택하는 부분 |
|---|---|---|
| [BERGEN 논문, Findings of EMNLP 2024](https://aclanthology.org/2024.findings-emnlp.449/) | RAG 구성과 평가를 재현 가능하게 비교하기 위한 연구 라이브러리 | 검색·재정렬·생성 연결 및 공개 설정 |
| [BERGEN 공식 코드](https://github.com/naver/bergen/tree/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212) | 위 연구의 구현 | 고정된 소스와 설정을 출발점으로 사용 |
| [KILT 논문, NAACL 2021](https://aclanthology.org/2021.naacl-main.200/) | 공통 Wikipedia 자료를 사용하는 지식 기반 과제 벤치마크 | 질문·정답·출처와 공통 자료 |
| [KILT 공식 데이터 설명](https://github.com/facebookresearch/KILT#kilt-data) | 데이터 구조, 분할, provenance 설명 | Natural Questions와 근거 매핑 |

BERGEN은 실행 도구이고, KILT는 데이터와 평가 자료다. 임베딩 모델과 생성기를 하나로 강제하는 세계 공통 표준은 아니다. 이번 연구에서는 공개된 구성요소를 선택하고 그 조합을 고정한다.

BERGEN 소스는 조사에서 확인한 **`eb8ec046eb6cf08be95b035b2d3bcc4b241ff212`**를 출발점으로 고정한다. 이 SHA만으로 Python 의존성, Hugging Face 모델·데이터 revision까지 고정되지는 않으므로 실제 준비 단계에서 각각 기록한다.

상용 생성 API, Jev 연결, 공통 인용 프롬프트, 축소 corpus, 시간·비용 계측은 우리의 변경 사항이다. 논문에는 **“BERGEN에 기반한 통제 비교 실험”**으로 기술하고, 기존 논문 성능의 완전 재현이나 공식 KILT 리더보드 결과라고 표현하지 않는다.

## 4. 비교군의 구현 명세

### 4.1 공통 자료 형식

각 passage는 다음 정보를 가진다.

| 필드 | 내용 |
|---|---|
| `passage_id` | 원본 자료와 분할 위치에 연결되는 고유 ID |
| `wikipedia_id` | 원본 Wikipedia 문서 ID |
| `title` | 문서 제목 |
| `text` | 제목과 분할 본문 |
| `source_span` | 정답 근거 매핑을 위한 원본 문단·문자/단어 위치 정보 |

KILT100w는 **100토큰이 아니라 본문을 공백 기준 100단어씩, 겹침 없이 분할**하고 각 조각 앞에 제목을 붙인다. 현행 processor는 일부 bullet 표시 문단을 제외하고 section 표시도 변환한다. 이 처리와 근거 위치 매핑을 함께 검수한다. [고정한 분할 코드](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/modules/dataset_processor.py#L312)

A/B/C/D 모두 같은 제목·본문·ID를 사용한다. C/D는 공유한 tree 외에 정답 문단을 더 상세히 제공하지 않는다. 최종 LLM에는 선택된 ID에 해당하는 공통 원문을 전달한다.

### 4.2 A: 기본 벡터 RAG

| 설정 | 값 |
|---|---|
| 임베딩 모델 | `Shitao/RetroMAE_MSMARCO_distill` |
| 문장 표현·유사도 | CLS pooling, dot product |
| 모델 입력 한도 | `max_len=256` |
| 검색 후보 수 | 50 |
| 생성에 전달할 근거 | 순위 상위 5개 |
| 재정렬 | 사용하지 않음 |

공식 `retromae` 설정을 사용한다. 문서 임베딩은 구축 단계에서 미리 만들고, 질문 임베딩과 검색은 온라인 질문 처리에 포함한다. [RetroMAE 설정](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/config/retriever/retromae.yaml), [후보 수 설정](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/config/rag.yaml)

현행 BERGEN dense 경로는 저장된 PyTorch 임베딩 tensor에 전수 dot product를 계산하는 검색이다. 이를 FAISS 근사 최근접 검색이라고 기술하지 않는다. 축소 corpus마다 별도 인덱스와 정확한 ID 매핑을 만든다. [검색 구현](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/modules/retrieve.py)

### 4.3 B: 같은 검색 + DeBERTa-v3 재정렬

| 설정 | 값 |
|---|---|
| 첫 검색 | A와 동일한 RetroMAE |
| 재정렬 모델 | `naver/trecdl22-crossencoder-debertav3` |
| 모델 입력 한도 | `max_len=256` |
| 재정렬 후보 수 | 50 |
| 생성에 전달할 근거 | 재정렬 순위 상위 5개 |

B는 A의 상위 50개를 질문과 함께 평가해 순서를 바꾼다. 검색되지 않은 문단을 재정렬기가 새로 찾아내지는 않는다. [DeBERTa-v3 설정](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/config/reranker/debertav3.yaml)

A/B 차이를 재정렬 추가로 제한하기 위해 이번 주 비교에는 BM25·dense 결합을 추가하지 않는다. 별도 강한 비교가 필요하면 BERGEN의 SPLADE-v3 + DeBERTa-v3 조합을 같은 생성 API로 평가한다. SPLADE는 학습된 sparse 검색이며 BM25·dense hybrid와 구분한다. 이 추가 결과 없이 모든 RAG 구성에 대한 우위를 주장하지 않는다. [SPLADE-v3 설정](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/config/retriever/splade-v3.yaml)

### 4.4 C: Jev가 공통 corpus에서 직접 근거 선택

첫 구현은 passage ID를 선택지로 사용하는 Jev Choice 판단을 기반으로 한다. 공식 Line-by-line search는 원문 ID의 Choice 순위와 답 존재 여부를 판단하는 Noul을 함께 보여준다. Choice의 확률 합은 1이므로 1위가 존재한다는 사실만으로 정답 근거가 있다는 뜻은 아니다. [TypeSafe 공식 예제](https://docs.typesafe.ai/cookbooks/semantic_find)

규모 확장을 위한 초기 선택 정책은 다음과 같다. 이 정책은 우리 설계이며, 검증된 최적 설정이라고 가정하지 않는다.

1. 공통 corpus를 질문과 무관한 고정 순서로 나눈다. 첫 창의 상한은 100개 passage다. 선택한 Jev 버전의 실제 입력·선택지 한도가 더 작으면 창을 더 나누고 그 결과를 기록한다.
2. 모든 창에 질문을 제공하고 Choice로 각 창의 상위 5개를 남긴다. 한 질문 안의 창 호출은 최대 8개까지 병렬 실행한다.
3. 남은 후보가 한 창의 한도보다 많으면 같은 방식으로 다시 나누고 상위 5개씩 남기는 단계를 반복한다.
4. 마지막 후보를 하나의 창에서 함께 판단하고 최종 상위 5개를 선택한다.
5. 선택한 ID의 원문을 공통 LLM에 전달한다.

서로 다른 창의 Choice 확률을 그대로 비교해 전역 순위를 만들지 않는다. 다음 단계에서 후보를 함께 다시 평가한다. 모든 창의 통과 후보 수, 단계 수, 근거가 탈락한 단계, 호출 수를 저장한다.

주 비교 C에서는 Noul 점수로 미리 답변을 거절하지 않는다. 답변 보류는 세 방법 모두 공통 생성 프롬프트가 담당한다. Noul 기반 사전 거절은 무근거 질문을 추가할 때 별도 실험으로 평가하고, 호출 비용도 추가한다.

Jev가 문서 전체를 한 요청으로 처리할 수 있다고 가정하지 않는다. 긴 문단, 후보 조합, 호출 제한으로 생기는 실제 비용과 실패를 측정한다.

## 5. 데이터 분할과 규모 실험

### 5.1 개발·평가 질문

KILT NQ에는 정답이 공개된 train과 validation이 있다. BERGEN의 `kilt_nq` 설정은 validation을 dev로 사용하고 test는 지정하지 않는다. KILT 공식 test 정답은 공개하지 않는다. [BERGEN 데이터 설정](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/config/dataset/kilt_nq.yaml), [KILT 데이터 설명](https://github.com/facebookresearch/KILT#kilt-data)

이번 연구의 분할은 다음과 같이 정한다.

| 용도 | 출처·규모 | 사용 방식 |
|---|---|---|
| 개발·파일럿 | KILT NQ train에서 100문항 | 연결 검증, 설정·선택 정책·예산 점검. 모델을 추가 학습하는 용도는 아님 |
| 본 평가 | KILT NQ validation에서 500문항 | 설정을 고정한 뒤 평가 |
| 추출 규칙 | seed `20261003`, 고정 ID 목록 | 제외 사유 검수 후 추출하며 목록과 데이터 hash 공개 |

근거를 추적할 수 없는 질문의 제외 기준을 추출 전에 정한다. 분할 변환으로 표·bullet 등의 근거가 사라지는 사례를 기록하고, 구현 결과가 나쁘다는 이유로 문항을 제외하지 않는다.

500문항은 첫 본 실험의 계획 규모다. 질문 ID 목록은 아직 생성하지 않았다. 평가 결과를 보고 설정을 바꾼다면 해당 평가 자료를 더 이상 미사용 평가 세트로 취급하지 않는다.

### 5.2 공통 축소 corpus

원래 KILT Wikipedia는 매우 크다. 첫 실험은 모든 방법이 접근하는 **하나의 공통 축소 corpus**를 만들고 규모를 늘린다.

1. 개발·평가 질문의 provenance를 원본 위치에 연결한다.
2. 근거를 보존하는 100단어 조각을 모아 공통 근거 집합 `G`를 만든다. 정답 문자열의 단순 포함 여부만으로 근거를 판정하지 않는다.
3. 같은 Wikipedia 자료에서 고정 seed로 배경 passage를 뽑아 `G`에 추가한다.
4. `N0 = max(1000, 1000 × ceil(|G| / 1000))`으로 첫 corpus 크기를 정한다.
5. `N0`, `5 × N0`, `20 × N0`의 세 nested corpus를 만든다. 앞 규모의 passage를 뒤 규모에도 유지한다.
6. 모든 규모에서 같은 평가 질문과 정답을 사용한다.

예를 들어 `N0=1000`이면 1천·5천·2만 passage를 비교한다. corpus는 질문마다 바꾸지 않으며, Jev와 RAG에 똑같이 제공한다. corpus 구성에 근거 라벨을 사용하는 것은 공개된 평가 자료 구성 절차다. 라벨은 온라인 선택기·생성기에 제공하지 않는다.

KILT provenance의 원래 문서/문단 위치와 BERGEN의 Wikipedia article 단위 검색 라벨을 구분한다. **문서 ID가 맞는 조각이라고 해서 그 조각 자체가 정답을 뒷받침한다고 간주하지 않는다.** 원본→변환 passage 매핑을 먼저 검증하고, 정확한 근거 매핑을 확보하지 못하면 passage recall을 보고하지 않는다. [라벨 처리](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/modules/processors/kilt_dataset_processor.py), [article 단위 평가 매핑](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/modules/rag.py#L320)

이 실험은 정답 근거를 보존한 **KILT 기반 규모 통제 실험**이다. 전체 Wikipedia의 검색 난이도나 실제 사내 corpus 분포를 그대로 재현하지 않는다. 배경 passage에 대체 정답 근거가 있을 수 있으므로 미주석 자료를 모두 무관한 자료로 단정하지 않는다.

각 corpus의 원문 목록·ID·hash·근거 매핑을 고정하고, A/B 인덱스를 해당 corpus에서 다시 만든다. full-corpus 검색 결과를 필터링한 파일로 축소 corpus의 실제 검색을 대신하지 않는다.

### 5.3 후속 조건

첫 본 실험 후 확장할 조건은 다음과 같다.

| 조건 | 추가로 확인할 내용 |
|---|---|
| 다중 근거 | KILT HotpotQA 등을 별도 분할하여 필요한 근거의 동시 확보와 답변 정확도 측정 |
| 자료에 답이 없음 | 공통 corpus 전체를 기준으로 답 부재를 검수한 별도 질문 집합 사용 |
| 유사한 방해 자료·순서 변화 | 같은 질문에서 품질·지연·비용이 얼마나 변하는지 측정 |
| 문서 갱신 | 추가·수정·삭제 후 구축/갱신 시간과 비용, 오래된 근거 사용 측정 |
| 한국어·이미지 | 자료 형식과 전처리, 모델 지원 범위를 확정한 별도 실험 |

NQ의 정답 근거를 제거했다는 이유만으로 답 부재를 확정하지 않는다. 다른 문단에 답이 남아 있을 수 있다. 초기 NQ 결과만으로 할루시네이션 감소나 사내 챗봇 구축 우위를 입증했다고 표현하지 않는다.

## 6. 공통 생성기와 실행 조건

최종 생성은 세 방법 모두 **같은 상용 LLM API와 동일 모델 버전**을 사용한다. 실제 모델 ID, Jev 버전, 가격 및 호출 예산은 API 준비 단계에서 고정한다. 공개되지 않은 판단 API를 실험 전제로 삼지 않는다.

| 조건 | 초기 실행 규칙 |
|---|---|
| 최종 근거 | 최대 5개 passage, 제목·ID 포함 |
| 근거 입력 예산 | 공통 생성 모델 기준 최대 2,000토큰 |
| 전체 입력 예산 | 시스템 프롬프트·질문·근거 합계 최대 4,096토큰 |
| 출력 예산 | 답변 JSON에 충분한 한도로 통일. 초기 목표 256 출력 토큰 |
| 생성 설정 | 지원되는 경우 temperature=0. 지원되지 않는 옵션과 추론 설정은 실제 값으로 기록 |
| 질문 동시성 | 1. 질문 내부 Jev 창 호출 동시성 상한은 8 |
| 반복 | 같은 질문·방법·규모 조합을 3회 실행 |
| 실행 순서 | 방법 순서를 seed로 섞어 시간대·서비스 부하 편향 완화 |
| 실행 환경 | 동일한 orchestration 환경, A/B의 고정된 검색·재정렬 장치와 설정 |
| 결과 캐시 | 온라인 지연 측정 중 검색 결과·질문 임베딩·Jev/LLM 응답 재사용 금지 |
| 준비 비용 | 문서 임베딩·인덱스·모델 로딩은 온라인 지연과 분리하여 구축/시작 비용에 기록 |

동일 근거 예산은 상한을 맞춘다는 뜻이다. 실제 사용량을 같게 강제하여 토큰 차이를 지우지 않는다. 예산이 넘는 경우 낮은 순위 passage부터 제외하며, 실제 전달한 ID·본문·토큰을 저장한다.

공통 프롬프트는 근거만으로 간결하게 답하고, 부족하면 답변을 보류하며, 사용한 근거 ID를 반환하도록 한다. 출력은 다음 구조를 사용한다.

```json
{
  "answer": "short answer or INSUFFICIENT_EVIDENCE",
  "evidence_ids": ["P001", "P017"]
}
```

EM/F1은 JSON 전체가 아니라 `answer` 필드에 계산한다. `evidence_ids`는 선택된 자료에 실제로 존재하는지와 답변을 지지하는지를 따로 검수한다. 파싱 실패·출력 잘림은 실패로 기록하며 조용히 성공 응답만 남기지 않는다.

모델 내부 추론 사용량이 출력 제한에 포함되는 API에서는 파일럿으로 충분한 공통 제한을 확인한 뒤 본 평가 전에 고정한다. API의 자동 prompt cache는 실제 적중·요금 정보를 기록하고, 로컬 응답 재생과 구별한다.

## 7. 평가 지표: 세 핵심 축과 진단

### 7.1 핵심 결과

| 축 | 주 지표 | 함께 보고할 내용 |
|---|---|---|
| 정확도 | 최종 답변 EM, token F1 | 답변 보류·파싱 실패 포함 전체 질문 기준, 질문별 정답 판정 |
| 속도 | 질문당 전체 응답 시간 p50/p95 | 평균, 선택·재정렬·생성 시간, 호출 수, 실패·재시도 |
| 토큰·비용 | 단계별 입력/출력 사용량, 질문당 금액 | 1천 질의 환산 비용, 구축비를 포함한 비용, 캐시·추론 토큰 |

BERGEN의 정규화와 EM/F1 구현을 출발점으로 사용한다. 정답이 여러 표현을 허용하면 허용 정답 목록을 유지한다. 주 지표를 실행 전에 고정하고, 결과를 본 뒤 유리한 Match 지표만 선택하지 않는다. [공식 QA 지표 코드](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/modules/metrics.py)

전체 시간은 **이미 준비된 corpus에 질문이 들어온 순간부터 최종 답변이 수신·파싱될 때까지**다. 질문 임베딩, 실제 검색, Jev의 모든 선택 단계, 프롬프트 구성, 네트워크, 재시도를 포함한다. 답변 품질 평가 시간은 포함하지 않는다.

### 7.2 비용 산정

질문당 온라인 비용은 다음 구성으로 계산한다.

```text
온라인 비용(q)
  = 검색·임베딩·재정렬의 유료 호출 비용
  + Jev 전체 단계의 호출 비용
  + 최종 LLM 호출 비용
  + 해당 실행에 배분한 검색·재정렬 계산 자원 비용

M개 질문의 총 운영 비용
  = 최초 구축 비용
  + 그 기간의 자료 갱신 비용
  + M개 질문의 온라인 비용 합계
```

실제 API usage 원본과 실행 시점 공식 가격표로 추정 금액을 산출하고, 가능하면 계정 청구 내역과 대조한다. **usage 기반 예상 요금과 실제 청구액을 구별한다.** 평가자 호출 비용은 실험 수행비로 따로 기록한다.

로컬 RetroMAE/DeBERTa에 API 청구 토큰이 없더라도 계산이 무료인 것으로 처리하지 않는다. 장치·계산 시간과 비용 배분 기준을 공개한다. 개인 장비의 금액을 확인할 수 없으면 측정 자원량과 API 비용을 분리해 보고하고, 전체 금액이 확인된 것처럼 쓰지 않는다.

모델마다 토크나이저·청구 단위가 다르므로 서로 다른 API 토큰 합계만으로 경제성을 결론 내리지 않는다. 원시 사용량은 구성요소별로 제시하고 금액은 공통 통화로 비교한다. RAG 문서 임베딩 구축비와 Jev의 반복 전체 자료 판단비도 포함한다.

구축 비용을 제외한 온라인 비용과, 100·1,000·10,000질의에 구축비를 나눠 반영한 평균 비용을 함께 제시한다. 유지보수 비용은 실제 갱신 실험을 했을 때 추가한다.

### 7.3 결과를 설명하는 진단 지표

| 항목 | 용도 |
|---|---|
| 근거 Recall@5/50 | 선택 단계가 정답 근거를 보존했는지 확인. article 수준과 검수된 passage 수준을 구별 |
| 근거 지지율 | 답변이 인용한 원문에 의해 뒷받침되는지 확인 |
| 불필요한 거절 | 답이 있는 질문에서 보류한 비율 |
| 무근거 답변 | 답이 없는 별도 질문에서 단정적으로 답한 비율 |
| 실행 실패 | 오류·timeout·파싱 실패·재시도 비율 |
| 구축·갱신 부담 | 실제 작업·계산 시간과 변경 범위. 코드 줄 수만으로 손쉬움을 판정하지 않음 |

근거 평가에는 방법 이름을 가린 사람 검수 또는 독립된 평가 절차를 사용한다. Jev를 C의 최종 품질 판정자로 사용하지 않는다. 단순한 정답 문서 검색 성공과 실제 인용 지지를 구별하는 평가는 [NIST TREC 2025 RAG 평가](https://trec.nist.gov/pubs/trec34/papers/Overview_rag.pdf)를 참고한다.

## 8. 공정 비교와 통계 처리

- 모든 방법에 같은 corpus·질문·생성 프롬프트·근거/출력 상한을 적용한다.
- corpus 구축용 라벨은 온라인 코드에서 접근하지 못하게 분리한다. 주 실행에서 oracle provenance를 사용하지 않는다.
- A와 B는 각각 독립 실행에 필요한 질문 임베딩·검색 시간을 측정한다. A에서 계산한 결과를 B에 무료로 재사용한 지연을 대표값으로 쓰지 않는다.
- 모든 방법이 같은 timeout·재시도 상한을 사용한다. 실패한 질문을 제외한 정확도만 보고하지 않는다.
- 지연은 성공 응답의 분포와 함께 전체 실행의 실패·timeout을 제시한다. 더 많이 실패한 방법이 빠른 것으로 보이지 않게 한다.
- 동일 질문의 방법별 차이를 짝지어 비교하고, 질문을 단위로 한 bootstrap 95% 신뢰구간을 제시한다. 3회 반복을 서로 독립인 새 질문처럼 세지 않는다.
- 설정 튜닝은 개발 세트에서 수행한다. 본 평가의 정답이나 oracle 결과를 이용해 선택 정책을 조정하지 않는다.
- 정확도·속도·비용의 우위는 해당 조건의 효과 크기와 불확실성으로 보고한다. 비열등성 기준을 사전에 정하지 않았다면 “동등한 정확도”라고 단정하지 않는다.

결론은 A 대비, B 대비, 규모별로 나눠 작성한다. full corpus나 다른 검색기·언어·과제를 실행하지 않았다면 그 범위의 승패를 추론하지 않는다.

## 9. BERGEN에서 추가 구현할 부분

BERGEN을 설치하는 것만으로 이번 실험이 완성되지는 않는다.

| 부분 | 확인한 상태와 해야 할 일 |
|---|---|
| 데이터 | 공통 축소 corpus, 근거 위치 매핑, 고정 질문 목록을 준비 |
| A/B | 공식 모델 설정을 연결하고 corpus별 인덱스·ID·길이 잘림을 검증 |
| C | Jev 직접 선택 adapter와 창 분할·후보 병합·원문 반환을 구현 |
| 공통 생성 | 같은 상용 API adapter와 답변/인용 프롬프트를 사용 |
| 실제 지연 | cached run을 읽는 경로와 분리하여 온라인 질문별 실행을 계측 |
| 실제 비용 | API usage·실행 시점 가격·재시도·캐시 및 계산 자원 기록 |
| 재현 자료 | 코드 SHA, 의존성 lock, 모델/data revision, 설정·프롬프트 hash 저장 |

공식 `generation_time`은 생성기 평가만 감싸므로 검색·재정렬을 포함한 전체 시간으로 사용하지 않는다. BERGEN은 저장된 검색·재정렬 결과를 재사용할 수 있으므로 온라인 지연 측정에서는 실제 선택이 실행되는지 확인한다. [시간·캐시 처리](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/modules/rag.py)

고정 revision의 상용 API wrapper는 호출에 `model/messages`만 전달하고 가격을 코드 안에 저장한다. 따라서 설정 파일의 출력 한도·temperature가 실제 적용된다고 가정하지 않으며, 이번 실험용 adapter에서 이를 검증하고 usage 원본을 기록한다. [공식 wrapper 코드](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/models/generators/llm_openai.py#L31)

공식 설치 안내는 Python 3.10과 CUDA 환경을 제시하고, dense 검색·재정렬 구현에도 CUDA 경로가 있다. 최종 생성기를 API로 바꿔도 이 검색 경로의 실행 환경 점검은 필요하다. 현재 컴퓨터의 GPU·네이티브 Windows 실행·대체 환경 설치는 아직 검증하지 않았다. 필요한 검색/재정렬/API 구성의 의존성을 먼저 확인한 뒤 전용 환경을 준비한다. [설치 안내](https://github.com/naver/bergen/blob/eb8ec046eb6cf08be95b035b2d3bcc4b241ff212/documentation/INSTALL.md)

## 10. 질문별로 남길 실행 기록

최소 기록 단위는 `질문 × 방법 × corpus 규모 × 반복`이다.

| 기록 묶음 | 필수 내용 |
|---|---|
| 식별 | experiment ID, 질문 ID, A/B/C/D, corpus hash·크기, 반복 번호 |
| 버전 | BERGEN/우리 코드 SHA, 모델·API ID, 프롬프트·설정 hash |
| 선택 | 실제 접근한 corpus, 단계별 후보 ID·점수, 최종 전달 ID와 본문 |
| 시간 | 질문 시작/종료, 단계별 경과 시간, 병렬 상한, API 대기·재시도 |
| 사용량 | 공급자별 원시 usage, 입력/출력/추론/캐시 사용량, 호출 수 |
| 비용 | 가격표 기준일·단위, 예상 금액, 확인 가능한 청구액, 계산 자원 배분 |
| 결과 | 원시 응답, 추출 답변·인용, EM/F1, 실패 사유, 근거 검수 |
| 데이터 | 정답·근거·split 라벨은 평가 기록에만 보관 |

API 키와 인증 헤더는 기록하거나 공개하지 않는다. 재현 공개물에는 고정된 질문·corpus 생성 절차, ID/근거 매핑, 설정, 실행 결과와 집계 코드가 포함되어야 한다.

## 11. 직접 겹치는 선행 실험과 연구 기여

가장 가까운 공개 자료는 아래 세 가지다. 같은 가설을 다룬 자료가 있으므로 “Jev로 RAG 검색을 대체하는 최초 제안”을 전제하지 않는다.

| 자료 | 이번 연구와 겹치는 내용 | 이번 연구에서 보완할 부분 |
|---|---|---|
| [Samelogic: Can Jev replace RAG or just improve retrieval?](https://samelogic.com/blog/can-jev-replace-rag-or-just-improve-retrieval) | Jev의 직접 근거 선택과 RAG를 비교하고 같은 생성기로 최종 답변까지 확인 | 소규모 자체 작성 자료를 넘어 공개 과제·고정 분할·규모 실험·전체 시간/총비용을 함께 측정 |
| [erendikmenn/jev-rag-benchmark 결과](https://github.com/erendikmenn/jev-rag-benchmark/blob/main/reports/generated/xquad-tr-hierarchical-sample100/comparison.md) | 전체 passage에 Jev를 계층 적용하고 검색 품질·지연·비용 비교 | 보고된 실험은 생성 없이 검색을 평가. 공통 최종 LLM을 포함한 전체 시스템 비교 필요 |
| [aifabrice/jev-rag NFCorpus 실험](https://github.com/aifabrice/jev-rag/blob/main/benchmarks/NFCORPUS_RESULTS.md) | Jev Line Search로 전체 corpus를 훑는 방식과 검색 파이프라인 비교 | 검색 benchmark와 최종 QA 결과를 구별하고, 동일 조건의 전체 응답 시간·비용을 기록 |

위 자료는 저자가 공개한 프로젝트·실험 보고서로 읽었으며, 동료 심사를 거친 동일한 전체 시스템 논문으로 확인한 것은 아니다. 공개 결과의 수치를 직접 재현하지 않았다. 일부 관련 실험에는 Jev가 기존 검색보다 불리한 결과도 있으므로 우위를 전제로 설계하지 않는다.

이번 연구의 기여 후보는 다음과 같다.

> 공개 데이터와 문헌 기반 RAG 구성을 사용하여, Jev 직접 선택과 RAG를 동일한 상용 생성 API 아래에서 비교하고, 정확도·전체 응답 시간·총비용의 변화 및 자료 규모에 따른 적용 경계를 재현 가능한 실험으로 밝힌다.

이것은 검증할 기여이며, 아직 얻은 결과가 아니다. 기존 자료와 차이가 있다는 사실만으로 신규성이나 게재 가능성이 확정되지는 않는다.

## 12. 논문에 방법과 도구를 쓰는 방식

방법 설명의 초안은 다음과 같다. 실제 완료된 범위와 사용 버전으로 갱신한다.

> 본 연구는 BERGEN을 기반으로 실험을 구성하고 KILT Natural Questions와 공통 Wikipedia passage 집합을 사용한다. RetroMAE 검색, 동일 검색에 DeBERTa-v3 재정렬을 추가한 구성, 공통 corpus에 대한 Jev 직접 근거 선택을 비교한다. 모든 구성은 동일한 상용 LLM 생성 API와 근거·출력 예산을 사용한다. 공개 근거 라벨을 보존한 nested corpus에서 최종 QA 정확도, 온라인 전체 지연, API 사용량 및 구축·질의 비용을 측정한다.

BERGEN·KILT 논문과 실제 사용 모델·Jev 자료를 인용하고 코드 revision을 명시한다. 상용 생성기, prompt, corpus 축소, Jev 정책, 지연·비용 계측이 원래 설정과 달라진 점을 적는다.

“BERGEN이 인증한 성능”, “공식 benchmark 전체 재현”, “모든 RAG보다 우수” 같은 표현은 사용하지 않는다. 원래 논문의 공개 수치를 생성기가 달라진 우리의 결과와 같은 조건의 결과처럼 직접 비교하지 않는다.
