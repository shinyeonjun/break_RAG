# C: 자연어 트리와 Jev 근거 탐색

2026-10-03 구현 기준. 질문·라벨을 읽지 않고 준비한 자료 트리를 여러 갈래로 탐색하고, 실제 원문에서 필요한 근거를 모은 뒤 공통 GPT-6 Luna에 전달한다. C는 임베딩·벡터 검색·BM25·A/B 검색 후보를 사용하지 않는다. 2026-10-04에 D 비교군을 추가했다. D는 같은 Jev 준비 트리와 탐색 규칙을 local Laya Multilingual로 실행한다. 따라서 C와 D의 온라인 판단 엔진 비교이며, D의 독립 자료 적재/트리 구축 성능 비교가 아니다. 정확도·속도·비용의 우위는 실험으로 검증할 가설이다.

## 역할과 사전 준비

코드는 트리·원문 위치·탐색 상태를 저장한다. Jev는 의미 판단을 한다. 모델의 세션 메모리에 의존하지 않고 각 요청에 질문, 현재 분기 설명 또는 필요한 원문을 전달한다.

1. 사람이 `config/c_taxonomy.json`에 분류체계와 자연어 설명을 정의한다. 초기 Wikipedia용 공간은 상위 8개 주제·말단 15개 범주다. 사람이 이 체계를 작성·유지하는 시간은 아직 측정하지 않았다.
2. `prepare_tree`가 공통 corpus의 각 원문 문단을 Jev **Choice**로 분류한다. 분기 경로·설명을 선택지로 전달하고, 질문셋·정답·근거 라벨은 읽지 않는다. 적재는 기본 16문단 단위로 준비한 뒤 실제 요청 크기에 맞게 나뉜다.
3. 선택한 범주와 Choice 확률이 0.20 이상인 대안 범주에 원문 참조를 둔다. 대안 확률은 단일 선택 분포의 불확실성으로, 독립적인 다중 라벨 확률은 아니다. 원본은 복사하지 않는다.
4. 범주 안에서 제목·ID 순서로 최대 8문단씩 묶고 **제목과 원문 첫 24단어**를 자료 카드로 남긴다. 생성 LLM 요약은 사용하지 않는다. 전체 원문을 보내는 단계와 이 설명 단계는 구분한다. 설명에 중요한 내용이 없으면 탐색에서 놓칠 수 있다.
5. `validate_tree`가 모든 공동 원문 ID의 접근 가능성, 순환·중복 노드·외부 원문 참조를 검사한다. SHA-256으로 트리·원문·설정·코드 버전을 묶는다. 실패한 적재는 체크포인트를 남기고 다음 실행에서 완료된 문단을 재사용한다.

새 분류체계를 넣을 수 있지만 DB/API 연결, PDF OCR, 이미지 판단, 자동 분류체계 생성은 이번 텍스트 QA 구현 범위 밖이다. C의 입력 원문은 A/B와 동일한 KILT100w 문단이다.

## 온라인 탐색

1. 현재 노드의 하위 분기마다 **Noul**로 “이 질문의 어느 부분에 필요한 근거나 구체적인 다음 탐색 단서가 여기에 있을 수 있는가?”를 독립 판단한다. 한 분기로 제한하지 않는다.
2. 초기 확률 0.45 이상인 여러 분기를 탐색한다. 나머지는 보류 큐에 둔다. 큐 우선순위는 경로에서 가장 낮은 판단 확률이며, 정확한 경로 확률로 해석하지 않는다. 기본적으로 한 차례에 최대 4개 노드를 연다.
3. 도달한 자료 묶음의 **전체 원문 문단**을 Score로 평가한다. 0=무관, 1=배경만 있음, 2=부분 근거·특정 출처 단서, 3=질문 일부의 직접 근거라는 네 단계 rubric이다. 반환 Score는 단계 인덱스의 기대값이다.
4. Score 1.5 이상 원문을 점수·ID 순서로 모으되, 공통 생성기의 `[ID] 원문` 형식에 대해 **2,000 o200k_base 텍스트 토큰** 예산을 지킨다. 원문 전체가 맞지 않으면 해당 문단을 제외하고 ID를 기록한다. 원문을 잘라 끼우지 않는다. 근거 개수는 고정하지 않는다.
5. 선택한 실제 원문으로 질문의 모든 사실·기간·단위·주체가 충족되는지 Noul로 확인한다. 확률 0.95 이상이면 중단한다. 이는 모델의 중단 판단이며 정답 보장이 아니다. 이 값이 높아도 오프라인 근거 라벨에서 실패할 수 있다.
6. 선택한 경로를 소진했는데 완결되지 않으면 보류 분기를 높은 우선순위부터 다시 연다. 여러 위치가 같은 원문을 가리켜도 Score와 반환은 한 번만 한다.

초기 한도는 질문당 API 32회, 원문 Score 128개, 노드 방문 256개, 보류 분기 재탐색 8회다. 큐 소진·완결성·각 한도에 따른 중단 이유, 방문 노드, 분기 확률, 원문 점수, 제외 ID, 확보한 원문을 모두 남긴다. 임계값·설명 길이·그룹 크기·탐색 폭은 개발셋에서 조정한 뒤 평가셋 실행 전에 고정해야 한다.

원문 속 출처 이름을 보고 관련 분기를 추가 탐색할 수 있는 여지는 있지만, 임의 URL·DB/API를 실행하거나 외부 문서를 내려받는 agent는 구현하지 않았다. 재탐색은 준비된 공통 트리 안에서만 수행한다.

## API, 입력 크기와 기록

공식 [API](https://docs.typesafe.ai/api) `POST /v1/systemone`을 사용하고 [모델 버전](https://docs.typesafe.ai/models)은 `jev-1.13.0`으로 고정한다. [Noul](https://docs.typesafe.ai/primitives/noul)은 질문별 yes 확률, [Choice](https://docs.typesafe.ai/primitives/choice)는 선택지와 분포, [Score](https://docs.typesafe.ai/primitives/score)는 점수와 분포를 반환한다. 공식 [계층 분류 예제](https://docs.typesafe.ai/cookbooks/hierarchical_classification)의 최종 한 경로 분류와 달리 C의 검색은 독립 분기 판단으로 여러 근거를 모은다.

요청은 최대 32질문·48,000 UTF-8 JSON 바이트로 나누고, state와 단일 질문은 24,000바이트로 제한한다. 이는 공식 컨텍스트 한도 내로 요청을 보수적으로 묶기 위한 가드다. Jev tokenizer를 직접 실행한 검증은 아니다. 입력 텍스트는 조용히 자르지 않고, 너무 큰 단일 요청은 실패한다. 실제 입력·출력 토큰은 제공사 `usage`만 사용한다.

실제 응답에서 확률의 소수점 두 자리 반올림을 확인했다. 원시 값을 재정규화하지 않고, 각 값의 반올림 구간 안에서 합계 1이 가능한지 검증한다. 모델·질문 ID·반환 종류·숫자 범위·Score와 분포의 일관성도 검사한다. 자동 재시도는 없으며 인증 헤더·키를 결과에 저장하지 않는다.

적재 checkpoint는 각 요청 후 저장된다. 첫 실호출에서 기존 검증기가 합계 0.99를 거부한 뒤, 수정된 검증기로 완료 350문단의 동일 요청 내용을 다시 확인하고 호환 checkpoint를 이관했다. 이전 해시·경로·사유는 `resume_provenance`에 남겼으며 실패 요청의 사용량도 비용에 포함했다.

## 평가와 저장

- `04_prepare_c_tree.ipynb`: 원문 적재·준비 시간·API 사용량·트리 접근 검증.
- `05_measure_abcd.ipynb`: A/B/C/D 저장 결과 품질 평가, 새 검색 지연, 새 검색과 공통 LLM 전체 응답을 각각 실행한다.
- A/B는 품질 평가에서 같은 dense 후보 ID·점수를 공유한다. C와 D는 동일한 준비 트리에서 각각 독립 판단 캐시를 보관한다. D local tokens·잘림·단계 시간은 Jev API usage와 분리한다.
- NQ와 HotpotQA의 한 유효 annotation에 필요한 모든 원문 span을 갖췄는지 오프라인 평가한다. 여러 자료 질문에서 일부만 찾은 결과도 남긴다. 답변은 별도 EM/F1로 평가한다.
- `results/<시간>_<ID>/`: 질문별 `retrieval.jsonl`, `system.jsonl`, CSV·요약·코드/모델/설정/원문 해시 manifest. 공통 LLM에 실제 전달한 프롬프트·ID·원시 usage를 포함한다.
- `results/c_requests/`: 실제 Jev 요청·응답·시간과 실패 진단. `results/d_requests/`: local Laya의 실제 state/questions·응답·usage·시간·잘림 거부. `results/partial/`: 완료한 검색·생성 결과의 즉시 기록.
- `data/c_trees/<해시>/`: C/D 공통 트리·적재 checkpoint·준비 manifest. `data/c_retrieval_cache/` 및 `data/d_retrieval_cache/`: 방법별 품질 평가 전용 캐시.

가격은 확인일·출처와 함께 설정에 저장한다. Jev는 [공식 안내](https://docs.typesafe.ai/models)의 입력 100만 토큰당 $0.042, 출력 무료 기준으로 사용량 비용을 추정한다. 준비 비용과 온라인 Jev 비용, 생성 LLM 비용을 분리한다. 사용량이 불명확한 실패는 비용 `None`으로 남긴다. 분류체계 작성 시간·로컬 GPU 금전 비용·갱신 비용은 아직 미측정이다.

A/B는 로컬 GPU, C는 원격 API로 실행한다. 네트워크와 요청 journal 쓰기도 C 온라인 시간에 포함된다. 처리량은 실제 측정한 단계·벽시계 기준을 명시하며, 이 배포 비교를 알고리즘 자체의 절대 속도로 일반화하지 않는다.

## 2026-10-03 최초 실행 검증

공통 2,000문단 전부를 실제 Jev API로 적재했고, 316노드·2,295원문 참조의 트리를 만들었다. 준비 누적 시간은 약 80.55초, 요청 251회, 입력 1,944,121토큰, 추정 API 비용 $0.081653082이다. 재개 전 실패한 반올림 검증 요청도 포함한다. 원문 2,000개 전부에 대한 접근을 검증했다. 이는 분류 정확도의 검증은 아니다.

테스트는 복수 분기 근거 확보·누락 경로 재탐색·중복 참조·호출 예산·원문 보존·토큰 예산·캐시 재생과 실제 호출 분리·적재 재개·API 계약·공통 생성기·증분 저장을 확인한다. 전체 평가 1,000문항, 다른 corpus 규모, 정책 보정, 업데이트·사람의 유지보수 부담 검증은 후속 실험이다.

05를 처음부터 끝까지 실행했고, 개발 NQ·HotpotQA 각 1문항에 대해 A/B/C 품질 평가·실제 검색·공통 LLM 생성 6회를 완료했다. 모두 원문 근거 라벨을 확보했다. HotpotQA 답변은 모두 `Focus`로 EM/F1 1, NQ는 모두 `I do not know`로 EM/F1 0이었다. NQ의 라벨 근거 회수 성공과 답변을 만들 수 있는 충분한 사실 확보는 구분해야 한다.

## 2026-10-04 전체 점검과 재실행

비용 계산의 비정상 usage·가격 처리를 수정하고 29개 테스트를 확인했다. 분류 기준·판단 요청·탐색 정책은 바꾸지 않았다. 이전 적재 요청 2,000개와 재조립한 동일 트리를 독립 검증한 뒤 `data/c_trees/d2d4a844189f3077e9d325ca/`에 호환 artifact를 저장했다. 원래 경로·체크포인트/manifest 해시·이관 사유는 `resume_provenance`에 남겼고 유료 재분류는 하지 않았다.

04를 다시 실행하여 완료 트리를 재사용했고, 05에서 같은 두 개발 질문의 A/B/C 검색·생성을 새로 실행했다. C는 NQ 21회·HotpotQA 26회 Jev 호출을 사용했고 두 질문 모두 `recovery_budget`으로 중단했다. 답변 EM/F1은 최초 파일럿과 같았다. 같은 질문의 사용량·지연은 별도 실호출마다 달라질 수 있으므로 최초 표와 새 런을 섞지 않는다.

점검 시 비교한 전체 시스템 런은 `20261004T012602_22979a7e`다. [전체 점검 기록](audit-2026-10-04.md)의 그림은 이 런의 관측을 보존한다. 이후 [06_compare_results.ipynb](../notebook/06_compare_results.ipynb)는 가장 최근의 완료 런을 자동으로 읽도록 변경했다. 05의 질문 수와 split은 `config/experiment.json`에서 바꾸며 기본값은 개발 각 20·평가 각 50이다. 이 새 측정은 사용자가 직접 실행한다. 06은 API를 호출하지 않는다.
