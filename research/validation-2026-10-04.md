# 입력 수정과 개발·평가 분리

단계 검증 실행은 [05_measure_abcd.ipynb](../notebook/05_measure_abcd.ipynb)의 기본 `WORKFLOW='staged'`, 결과 대조·시각화는 [06_compare_results.ipynb](../notebook/06_compare_results.ipynb)로 통합했다. 문항 수는 [validation_study.json](../config/validation_study.json)의 `questions_per_task`를 수정한다. 일반 직접 비교는 05의 `WORKFLOW='standard'`와 `config/experiment.json`을 사용한다. 06은 저장 결과만 읽으며 유료 호출을 하지 않는다.

## 보존한 기준

A는 RetroMAE로 50개 후보를 검색하고 5개를 반환한다. B는 같은 후보를 DeBERTa로 재정렬해 5개를 반환한다. C는 Jev API, D는 고정 Laya 체크포인트를 같은 자연어 분류 트리에서 사용한다. 원문 저장소·생성기·최대 근거 텍스트 예산·정답 규칙은 공유한다. 원래 설정과 과거 결과는 보존한다.

개발 NQ 20개와 HotpotQA 20개를 사용하고, 평가 NQ 50개와 HotpotQA 50개는 설정 선택 후 실행한다. 개발·평가의 질문 ID와 정규화된 질문 문자열에 교집합이 없음을 확인했다. 공통 2,000문단 코퍼스는 개발·평가의 정답 근거를 강제 포함한 축소 코퍼스다. 기업 자료 전체나 공식 전체 Wikipedia 벤치마크의 성능으로 해석하지 않는다.

## 수정 및 검사

Laya SDK의 `usage.truncated`는 지시문 헤더의 잘림을 충분히 보고하지 않았다. 대상 자료를 독립적인 state로 옮기고 짧은 작업 지시를 head에 둔다. 실제 SDK 패킹으로 지시문·선택지·본문을 모두 검사하고 잘림은 추론 전에 거부한다. 입력 3,701개 재생은 모두 보존됐지만, 이것은 추론 성능이나 지연 결과가 아니다.

추론은 공식 `predict_batch`를 사용하며 고정 체크포인트를 GPU에 한 번 로드한다. 원래 ID에 결과를 대응시키고, native 응답별 token usage와 잘림 진단을 요구한다. 일시적으로 CPU에 갔다 GPU로 복귀한 경우도 fallback counter로 거부한다. 실제 전달 토큰 ID와 원래 요청·응답을 모두 보관한다.

실제 원문에서 확인한 8개 개발 질문으로 분기·관련성·충분성 판단 48개를 검사했다. 레이블은 Jev의 출력을 복사한 것이 아니다. 이 작은 진단셋은 보정된 확률이나 일반 정확도를 입증하지 않는다. 점수 선택지 순서를 바꾸는 16개 추가 검사도 따로 기록한다.

## 개발에서만 설정 선택

C의 baseline, top2, top3, 동일 충분성 입력 재사용을 각각 새로 실행한다. top2/top3는 절대 점수 임계값 대신 순위를 사용한다. 재사용은 한 질문 안의 동일 state와 question에 한정하며 원문 내용과 순서가 달라지면 다시 호출한다. 서로 다른 변경을 결합하지 않는다.

D는 입력 수정만 하고 원래 임계값을 유지한 40문항 대조군을 먼저 실행한다. 별도 [D 후보 설정](../config/d_laya_candidate.json)은 분기 0.1, 충분성 0.8, 상위 3개를 사용한다. 여러 정책 변경이므로 단일 효과 실험이 아니다. 동일 40문항 결과로 두 정책 중 하나를 선택한다. 확률 보정이 완료됐다고 주장하지 않는다.

선택 순서는 개발 EM, 공동 근거 ID 확보율, 낮은 API 비용이다. 요약 CSV와 완료 해시가 있는 원시 JSONL을 대조한다. C/D의 설정·트리·검색 코드·클라이언트 서명을 저장한 뒤, 평가에서 서명이 일치해야 실행한다. 평가 라벨을 읽기 전 정책 파일을 저장한다. 평가 결과로 다시 튜닝하지 않는다.

## 계측과 해석

각 질문에서 방법 순서를 무작위로 섞고 새로운 검색과 생성 호출을 실행한다. 평가 프로세스는 하나이며 다른 실험을 동시에 실행하지 않는다. 이번 개발 C 실험과 A/B/D 대조군은 일부 시간에 겹쳤으므로 개발 지연은 탐색적 관측이다.

전체 시간은 실제 wall clock이며 원시 기록 비용을 포함한다. 검색·생성 단계의 합을 전체 시간으로 대신하지 않는다. GPU 모델은 같은 장치에서 워밍업한 뒤 사용한다. 문서 준비·모델 로딩·인덱스/트리 캐시 재사용은 온라인 비용과 별도로 기록한다. D는 C/Jev로 사전 준비한 같은 트리를 재사용하므로, 완전히 로컬인 적재 파이프라인을 검증한 것은 아니다.

API ledger는 물리 HTTP 요청을 한 번씩 센다. 비용은 저장된 usage와 단가의 추정이며 GPU·전력·유지보수 비용을 제외한다. 서로 다른 토크나이저의 토큰은 합산하지 않는다. 로컬 처리량은 기록된 토큰/단계 시간으로 정의하며 순수 GPU FLOPS와 다르다.

원래 EM/F1과 공동 근거 ID 지표는 유지한다. 네 가지 항목을 동시에 요구하는 개발 질문은 별도 component 지표를 추가했다. 인용 존재는 entailment 검증이 아니며, 일부 gold ID의 내용이 답에 충분하지 않은 문제는 표시만 하고 데이터를 삭제하지 않았다. 평가 질문 전체의 의미적 근거 충분성을 수동 감사한 것은 아니다.

반복은 한 번이다. 평가의 대응 부트스트랩은 질문 간 변동의 보조 분석이며 API 시간대 변동이나 전체 기업 자료에서의 불확실성을 추정하지 않는다.

## 저장과 확인

현재 실행 위치는 `results/current_staged_run.txt`에 있다. 실제 결과는 해당 `staged_*` 폴더의 `dev/<arm>`과 `eval/ABCD_frozen`에 증분 저장한다. `completed.json`이 없는 폴더는 완료된 결과가 아니다. 각 manifest의 `raw_log`가 실제 HTTP·모델 경계 기록으로 연결된다.

`frozen_c_policy.json`과 `frozen_d_policy.json`은 개발 선택, `eval/ABCD_frozen/policy_before_labels.json`은 평가 전 기록이다. 06에서 원시 결과·가격·프롬프트·A/B 후보·토큰 잘림·질문별 요약을 대조한 뒤 새 분석 폴더에 그림과 CSV를 저장한다.

코드 검증은 76개 통과, 1개 건너뜀이었다. Jev Review 점수는 보조 신호로 사용했고, 입력 보존 및 집계의 타당성은 실제 재생·실행·회귀 테스트로 확인했다.
