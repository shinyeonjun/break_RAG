# 판단모델 검색의 품질·지연·비용을 개선하기 위한 선행연구와 개발 실험

조사일: 2026-10-04. 범위: 기존 A/B를 보존하면서, 별도 임베딩 검색기가 후보를 먼저 제한하지 않는 판단모델 검색을 연구한다. 문헌 조사, 기존 원시 기록의 비용 검산, 07 개발 점수의 작은 오프라인 근사 실험을 수행했다. 새 모델 학습·유료 API 호출·엔진 수정·08 평가 재실행은 하지 않았다.

**가장 유력한 방향은 매 질문마다 전체 대표 설명을 다시 읽는 작업을 줄이고, 그 의미 판단을 오프라인 색인·학습·캐시에 옮기는 것이다.** 배치 크기나 요약 길이만 바꾸는 접근보다 구조적으로 큰 절감 여지가 있다. 어떤 문헌도 현재 Jev 구성의 세 축 동시 우위를 보장하지는 않는다.

## 1. 현재 결과와 개선해야 할 부분

“벡터 검색 제거”의 범위도 명확히 해야 한다. **온라인에서 RetroMAE 같은 별도 검색기를 쓰지 않는 것**, **벡터 최근접 검색 자체를 쓰지 않는 것**, **오프라인 문서 표현에도 임베딩을 쓰지 않는 것**은 서로 다른 조건이다. 신경망 내부의 수치 표현까지 없다는 주장은 하지 않는다.

### 2.1 ANNCUR: “AI가 점수를 주고 알고리즘이 탐색한다”에 가장 가까운 연구

원문의 실험은 ZESHEL의 entity linking이다. 평가하는 top-k recall은 **cross-encoder를 전수 실행했을 때의 상위 이웃을 얼마나 재현하는가**이며, 우리의 정답 근거 확보율과 다른 지표다. 원문은 특히 `k > 10`의 비용·회수율 trade-off를 보고하므로 최종 근거 5개 조건의 우위를 보장하지 않는다. [논문 본문 §2–3](https://aclanthology.org/2022.emnlp-main.140.pdf)

오프라인 기준 질문 집합을 `I`, 기준 자료 집합을 `J`라 두고, 실제 판단 점수 행렬을 `S`라 하면 간단한 CUR 확장은 다음 형태다.

\[
R=S_{I,:},\quad W=S_{I,J},\quad
c_q=[f(q,d_j)]_{j\in J},\quad
\widehat S_{q,:}=c_q W^{\dagger}R.
\]

새 질문에는 기준 자료 `|J|`개만 실제 판단하고 나머지 점수를 근사한다. 필요한 오프라인 판단은 기준 질문×전체 자료이며, 자료 갱신 때 해당 열도 다시 준비해야 한다. **우리 Jev 점수가 충분히 저랭크라는 것은 검증 전 가설**이다. 논문은 저랭크성을 개선하는 `[EMB]-CE` 모델 구조도 제안하며, 블랙박스 Jev에 그 구조를 적용할 수 있다는 뜻은 아니다. [원문 §2 및 한계](https://aclanthology.org/2022.emnlp-main.140.pdf)

첫 적용 대상은 2,000개 원문보다 **기존 개발 로그의 질문×100개 Macro 점수 행렬**이 좋다. 실제 점수 중 일부만 관측했다고 가정해 나머지를 재구성하고, teacher 순위 재현과 gold 그룹 완전 확보를 각각 평가한다. 이 단계는 기존 로그가 충분하면 새 API 없이 가능하다. 통과하더라도 Micro 원문 판단 비용은 별도로 남는다.

### 2.2 PECOS: 자료 설명을 반복해서 읽지 않는 다중 라벨 라우터

PECOS는 큰 유한 출력 공간의 관련 라벨들을 예측하는 문제다. 문서나 그룹을 라벨로 삼으면 질문→관련 그룹들이라는 구조에 연결할 수 있다. 원문에는 선형 matcher와 Transformer matcher의 학습·품질·추론 비용 차이가 명시돼 있다. 빠른 선형 모델의 수치를 Transformer 전체에 적용하면 안 된다. [논문 §3–4, §6](https://www.jmlr.org/papers/volume23/21-0085/21-0085.pdf)

우리에게 옮길 구체적인 가설은 다음과 같다.

\[
h_q=\operatorname{Encoder}(q),\quad
\widehat y_q=\sigma(W h_q+b)\in[0,1]^M.
\]

그룹 설명은 학습에 사용하고, 온라인에는 질문만 넣어 여러 그룹을 예측한다. sigmoid는 복수 그룹 선택을 허용하지만 그 값을 보정된 확률로 바로 취급하지 않는다. 이 식은 **제안하는 소규모 학생 라우터**이며 PECOS 원문 전체 구현과 동일하지 않다.

그룹·문서마다 실제 관련 질문과 어려운 비관련 질문이 필요하다. 정답 라벨을 Jev 출력 하나로 대체하면 teacher 오류를 복제할 수 있으므로 검수한 근거 라벨과 혼합한다. 새로운 그룹·문서를 추가하면 학습된 출력 공간과 연결 규약도 갱신해야 한다. 문서 수가 늘어도 비용이 상수라는 보장은 없다.

### 2.3 PreTTR: 온라인 판단 수보다 “판단 한 번의 반복 계산”을 줄인다

문서 부분을 질문과 독립적으로 계산하도록 하위 층의 상호작용을 제한하고, 그 결과를 저장한 뒤 상위 층에서 질문과 결합한다. 캐시의 압축도 학습한다. 저장 공간과 인덱싱 비용을 추론 시간 절감과 교환하는 방식이다. [원문 §4, Figure 2](https://arxiv.org/pdf/2004.14255)

**현재 Jev API 요청에 hidden-state 캐시를 붙일 수 있다는 근거는 없다.** Laya도 공개 체크포인트에 곧바로 적용할 수 있는 옵션이라고 가정하지 않는다. 로컬 모델 구조와 학습 코드를 변경하는 별도 연구다. 첫 검색 범위를 줄여 주는 기법이 아니므로 PECOS식 라우터 또는 다른 접근과 역할을 분리해 검증해야 한다.

### 2.4 DSI·NCI·SEAL: 온라인 의미 해석을 더 작은 ID·단서로 바꾼다

DSI는 문서와 ID의 대응을 모델 매개변수에 학습하고 질문으로 ID를 생성한다. 원문 부록에는 indexing과 retrieval 학습 사이의 망각 문제도 다룬다. 온라인에서 짧게 답한다는 장점과 corpus 학습·재학습 부담을 함께 봐야 한다. [DSI 본문 및 부록](https://arxiv.org/pdf/2202.06991)

NCI는 문서 BERT 임베딩을 계층 k-means로 나눠 의미 ID를 만들고, 생성한 질문으로 ID decoding을 학습한다. 따라서 **온라인 벡터 검색을 없애는 설계와 오프라인 임베딩을 쓰는 설계가 양립**한다. beam 폭과 디코딩 길이도 추론 비용이다. [NCI §3.1–3.2 및 효율 분석](https://proceedings.neurips.cc/paper_files/paper/2022/file/a46156bd3579c3b268108ea6aca71d13-Paper-Conference.pdf)

SEAL은 생성 단서가 원문에 존재하도록 FM-index로 제약하고, 여러 단서 점수를 문서에 연결한다. 원문 KILT passage 평가가 있어 데이터 계열은 가깝지만, 원문 생성기·전체 corpus·학습 조건은 우리의 2,000문단 실험과 다르다. 현재 Jev의 고정 출력 기능과도 다르다. [SEAL 논문](https://arxiv.org/abs/2204.10628), [공식 구현](https://github.com/facebookresearch/SEAL)

이들에서 가져올 공통 원칙은 **“온라인에 자료 전체를 읽히는 대신, 사전 학습한 ID/짧은 단서와 저장된 원문을 코드가 연결한다”**다. 현재 C의 요약을 길게 유지하면서 읽는 모델을 작은 모델로 바꾸기만 하는 설계와 다르다.

### 2.5 RankZephyr·PLAID: 학생 판단기와 계산 예산의 설계

RankZephyr는 teacher 순위의 로컬 이전, 다양한 후보 수, 입력 순서 섞기, 어려운 후보의 중요성을 보여 준다. 공개 결과는 **이미 검색된 후보를 재정렬하는 7B 모델**에 대한 것이다. Jev와 Laya의 파라미터 차이·출력 구조·학습 지원 범위를 무시한 성공 예측은 하지 않는다. [논문 §3](https://arxiv.org/pdf/2312.02724)

우리 C의 학생 판단기에는 실제 분기 설명, 한 질문의 일부만 뒷받침하는 문단, 주제만 비슷한 오답, 고유명사·연도·부정 조건, 선택지 순서 변경을 포함하는 것이 구체적인 연구 제안이다. teacher의 soft score와 원문 검수 라벨을 함께 쓰되, 평가 질문의 Jev 결과를 학습 데이터로 가져오지 않는다.

PLAID는 문서 전체의 비싼 표현을 항상 복원하지 않고, 공유 centroid 점수와 근사를 활용해 후보를 좁힌다. **원문의 속도 개선은 ColBERTv2에 대한 개선**이며 우리 B·C 시간의 예측값이 아니다. “값싼 1차 계산이 비싼 판단의 누락을 얼마나 만들었는가”를 독립적으로 측정하는 실험 구조가 참고할 부분이다. [논문 §4](https://arxiv.org/pdf/2205.09707)

## 3. 직접 겹치는 공식 Jev 구현도 존재한다

PageIndex 제작사 VectifyAI의 [jev-doc-search](https://github.com/VectifyAI/jev-doc-search)는 Jev와 PageIndex를 이용한 공개 구현이다. GitHub API 확인 기준 생성일은 2026-09-30이며, 이번에 읽은 코드는 커밋 `7b1008c437c8c9a88da8a427a76052fb0454977a`다. [저장소 메타데이터](https://api.github.com/repos/VectifyAI/jev-doc-search), [고정 코드](https://github.com/VectifyAI/jev-doc-search/blob/7b1008c437c8c9a88da8a427a76052fb0454977a/tree_search.py)

구현은 제목·요약의 트리에서 `Choice`로 경로를 선택하고 beam 3개를 유지한다. 말단 페이지 후보를 `Choice`로 고른 뒤 최대 16개를 `Noul`로 검증한다. 긴 페이지 후보는 창으로 나누며, 원문 읽기·재시도·검증 비용은 여전히 남는다. README에는 두 연차 보고서 질문의 데모가 있다. **학술 논문이나 현재 A/B 대비 품질·지연·총비용 동시 우위의 증거는 아니다.** [고정 README](https://github.com/VectifyAI/jev-doc-search/blob/7b1008c437c8c9a88da8a427a76052fb0454977a/README.md)

이 코드와 우리의 C는 순차 트리/2단계 평면 라우팅, 상대적 Choice/독립 Noul, 단일 페이지/복수 근거 등의 차이가 있다. 그러나 **“Jev로 자연어 트리를 검색한다” 자체만 신규 기여로 주장하기는 어렵다.** 후보 창마다 정규화된 상대 확률을 직접 비교하는 정책도 복사 전에 검증해야 한다. 연구 기여를 실제 호출량을 줄이는 색인 규약·학습·근거 보존 정책과 재현 가능한 trade-off로 구체화하는 편이 낫다.

## 4. 권고하는 개발 실험 순서

아래 표는 개발 순서의 제안이다. 1번의 단순 CUR 근사만 작은 오프라인 재생으로 실행했으며 결과는 §7에 기록했다. 나머지는 실행하지 않았다. **08의 원문·설정·로그·질문 ID를 수정하지 않고, 08에 반복해서 맞추는 최적화도 하지 않는다.** 이미 결과를 본 08은 보존하는 역사적 평가다. 새 구조를 개발 자료에서 고른 뒤, 기존 개발·평가 ID와 겹치지 않는 새 평가 질문을 고정해야 한다.

| 순서 | 작은 실험 | 새로 확인할 핵심 | 통과·중단 기준 |
|---|---|---|---|
| 1 | 기존 07의 Macro score matrix를 CUR로 재생. 질문 행을 학습용/검증용으로 분리하고 기준 그룹 4·8·16개부터 비교 | 일부 Jev 판단으로 100개 그룹 순위를 근사할 수 있는가? | teacher top-K 재현율과 gold 그룹 완전 확보를 따로 보고. 근사만으로 누락이 크면 대규모 API 실행 중단 |
| 2 | 기존 D 판단을 Macro/Micro로 분리해 오라클 교차 재생 | 그룹 선택 실패와 원문 판정 실패 중 어디가 지배적인가? | gold 그룹을 줬을 때도 Micro가 무너지면 먼저 원문 판정 학습. 품질이 없는 상태의 전체 속도 튜닝은 보류 |
| 3 | PECOS에서 아이디어를 가져온 질문 전용 다중 라벨 학생 라우터 | 온라인에 설명 100개를 주지 않아도 필요한 복수 그룹을 고를 수 있는가? | 질문을 분리한 검증에서 개발 B의 목표 근거 회수율을 만족하는 설정만 다음 단계로 이동 |
| 4 | C가 고른 원문 후보 분포로 로컬 관련성/근거 일부 판정기를 학습·검증 | 작은 학생이 실제로 C의 필요한 판단을 배우는가? | 어려운 오답·입력 순서·길이별 오류 보고. Jev 출력 일치와 gold 근거 성능을 혼동하지 않음 |
| 5 | 검증에서 실패 위험이 큰 질문에만 제한된 Jev fallback | 학생 경로와 교사 경로를 합친 평균 비용·품질이 목표를 만족하는가? | fallback 비율·실제 API 입력·p95 지연·누락을 포함. 불확실성 점수는 검증 자료에서 보정 |
| 6 | 필요할 경우 로컬 판단기를 PreTTR식 문서 캐시 구조로 별도 설계 | 반복 문서 계산을 실제로 줄일 수 있는가? | 온라인 지연 감소와 저장·학습·갱신 비용을 같이 보고. 호출 수 감소와 혼동하지 않음 |

CUR에서 사용하는 실제 점수 행렬이 Noul 확률이라면 보정 전 점수와 안정적으로 처리한 logit 변형을 개발 자료에서 비교할 수 있다. 0/1 근처 확률의 logit은 불안정하므로 clipping 규약도 사전에 고정한다. anchor 선택·변환·rank를 평가 결과를 보고 고르면 안 된다. 이것은 우리 점수에 적용할 **탐색 가설**이며 논문이 Jev에 대해 검증한 방법이 아니다.

학생 라우터의 학습 데이터는 실제 train 질문·검수한 근거, 또는 질문과 무관하게 corpus에서 만든 합성 질문을 사용할 수 있다. 문서 갱신 때의 자동 적재·라벨 확장도 실험해야 한다. 단순히 기존 평가 질문을 더 많이 teacher에게 물어 학습시키는 방식은 새 평가 성능의 근거가 될 수 없다.

## 5. 세 축에서 이겼다고 말하기 위한 조건

목표는 새 비교군 `C*`가 같은 질문·원문·공통 생성기·최대 근거 예산에서 더 좋은 답변 품질과 더 낮은 실제 비용·지연을 보이는 것이다. 원격 API 요금, 로컬 처리량·GPU 메모리, 준비·학습·갱신 비용을 분리하고 필요한 경우 사용 횟수로 준비비를 상각한다.

개발 단계에서는 `R_complete >= R0`를 만족하는 설정의 비용·지연 Pareto frontier를 찾는다. `R0`와 답변 개선 최소 폭은 개발 비교군에서 정하고 최종 평가 전에 고정한다. 최종 답변 EM/F1, 완전 근거 확보, 평균·p95 시간, 실제 API 사용량을 질문별로 남긴다. 세 축 동시 우위를 주장하려면 동일 질문의 paired 차이와 불확실성도 보여야 한다.

벡터 검색이 먼저 고른 후보에만 Jev를 적용하는 실험은 별도 hybrid 비교군이다. 속도를 위해 그런 구조를 사용할 수는 있지만 **첫 검색 대체라는 주 연구 질문과 결과를 합쳐서는 안 된다.** 반면 오프라인 학습 색인·문서 캐시·판단 점수 유도 표현은 첫 검색 대체 연구 안에서 검토할 수 있고, 사용한 수치 표현과 준비 비용을 명시해야 한다.

검증할 핵심 가설은 **“소수 의미 판단으로 전체 검색 점수를 확장할 수 있는가”(ANNCUR)**와 **“자료 설명의 의미를 작은 로컬 다중 라벨 라우터에 학습시킬 수 있는가”(PECOS)**다. 이번의 작은 근사 실험은 전자를 바로 확대할 근거를 주지 못했다. 현재는 후자를 우선 검토하되, 필요한 근거를 잃지 않는 조건과 원문 Micro 판단·공통 생성기까지 포함한 비용을 함께 확인하는 것이 타당하다.

## 6. 현재 요금·측정값에서의 손익분기

다음은 다른 논문의 수치를 옮긴 예측이 아니라 08의 실제 입력·비용을 이용한 조건부 계산이다. Jev `jev-1.13.0`의 공식 입력 단가는 확인일 기준 USD 0.042/백만 토큰, 출력은 무료다. [TypeSafe 모델·요금 문서](https://docs.typesafe.ai/models)

\[
p_J=\frac{0.042}{10^6}=4.2\times10^{-8}\;\mathrm{USD/token}.
\]

08의 질문당 평균은 다음과 같다. 원시 출처는 [비용 구성 CSV](../results/frozen_20261004T113957_ec67887a/analysis/input_and_cost_components.csv)와 [호출 로그](../results/raw/20261004T113957_fe63661f)다.

| 단계 | Jev 입력 토큰 | 물리 HTTP 요청 | Jev 요금 |
|---|---:|---:|---:|
| Macro: 그룹 100개 판단 | 74,770.725 | 7 | USD 0.00314037045 |
| Micro: 선택 그룹 안의 원문 100개 판단 | 32,025 | 4 | USD 0.00134505 |
| 합계 | 106,795.725 | 11 | USD 0.00448542045 |

Macro가 판단기 요금의 약 70%지만 **Macro 비용을 완전히 없애도 현재 Micro 요금만 B 전체 API 요금의 약 13.3배**다. 그룹 선택만 로컬로 옮기면 충분하다는 뜻은 아니다.

B 전체 API 요금과 현재 C 생성기 요금은 각각 다음과 같다.

\[
C_{B,\mathrm{API}}=0.0001014025,\qquad
C_{C,\mathrm{gen}}=0.00009982.
\]

새 판단기 입력량을 \(U_J\), 새 생성 요금을 \(C_{\mathrm{gen}}'\)라 할 때 B의 API 요금보다 낮아지려면

\[
p_J U_J+C_{\mathrm{gen}}'<C_{B,\mathrm{API}}
\quad\Longrightarrow\quad
U_J<\frac{C_{B,\mathrm{API}}-C_{\mathrm{gen}}'}{p_J}.
\]

| 생성 요금에 대한 가정 | 허용되는 Jev 입력 평균의 상한 |
|---|---:|
| 현재 C와 동일 | 약 37.7토큰/질문 |
| 현재 C의 절반 | 약 1,226토큰/질문 |
| 생성 요금이 0이라는 가상 최선 | 약 2,414토큰/질문 |

이것은 **이번 공통 생성기·현재 요금·현재 평균 기준의 API 청구액 조건**이다. 모든 질문의 한도, 미래 가격의 한도, 전체 운영비의 불가능성 증명이 아니다. 로컬 GPU·준비·학습 비용은 이 표에 포함되지 않는다. 그럼에도 현재 10.7만 토큰과의 차이 때문에 호출 묶기나 지시문 일부 축약만으로 45배의 API 비용 차이를 해결한다고 가정하기는 어렵다.

### 6.1 병렬 처리와 shared state의 실제 적용 범위

공식 예제의 12.2배 비용 절감은 **동일한 긴 문서 하나에 13개 질문을 묻는 상황**에서 문서를 한 번만 전달한 결과다. 10배 지연 개선의 비교 대상은 13개 단일 호출의 순차 실행이다. 서로 다른 그룹 설명 100개를 한 질문과 비교하는 우리의 입력량이 동일 비율로 줄어든다는 증거가 아니다. [공식 병렬 질문 예제](https://docs.typesafe.ai/cookbooks/parallel_questions)

현재 공식 한도는 요청당 64k토큰, `state`와 가장 긴 질문의 합은 32k토큰이다. 따라서 “한 요청으로 묶을 수 있는가”와 “한 요청이 읽는 전체 입력량이 작은가”를 구분해야 한다. [공식 모델 한도](https://docs.typesafe.ai/models)

같은 원문에 관련성·근거 종류 등 여러 판단을 수행할 때는 shared state 재사용을 확인할 가치가 있다. 서로 다른 자료를 큰 state로 합칠 때는 비용·한도·판단 간 자료 혼동도 함께 측정한다. 공식 문서 역시 큰 state의 불필요한 내용이 판단 품질을 떨어뜨릴 수 있음을 기록한다. [Jev 1.13 제한 사례](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

### 6.2 준비 비용과 조건부 교사 호출

새 구조가 오프라인에 corpus 정보를 학습한다면 요청당 총비용은 다음처럼 분리해야 한다.

\[
\overline C_{\mathrm{total}}(Q)=
\frac{F_{\mathrm{prepare}}+F_{\mathrm{train}}+F_{\mathrm{update}}}{Q}
+\frac1Q\sum_{q=1}^{Q}
\left(C_{\mathrm{local}}(q)+C_{\mathrm{API}}(q)\right).
\]

준비·갱신의 포함 기간과 GPU 비용 환산 방법을 먼저 정한다. 고정 비용이 높고 온라인 비용이 낮다면 사용 횟수에 따른 손익분기와 문서 갱신 주기가 성능만큼 중요하다.

학생 모델이 어려운 질문에만 Jev를 호출할 경우

\[
\mathbb E[C_{\mathrm{API}}]
=\mathbb E[C_{\mathrm{gen}}]
+p_J\mathbb E[\mathbf1_{\mathrm{fallback}} U_{\mathrm{fallback}}].
\]

조건부 호출 비율을 \(a\), 호출했을 때의 평균 입력을 \(\mathbb E[U_{\mathrm{fallback}}\mid\mathrm{fallback}]\)라 두면 마지막 항은 \(p_J a\mathbb E[U_{\mathrm{fallback}}\mid\mathrm{fallback}]\)다. 현재 생성 요금을 유지하고 fallback 한 번이 2,000토큰이라면 API 요금상 허용 비율은 약 1.88% 미만이다. 생성 요금을 절반으로 줄인다면 같은 입력에서 약 61.3% 미만이다. **이 숫자는 품질·지연 목표도 만족한다는 보장이 아니며**, 대부분의 질문에서 로컬 품질이 먼저 확보되어야 한다.

## 7. 비용 없는 개발 점수 근사 실험

ANNCUR의 아이디어를 바로 크게 실행하기 전에, 기존 07 로그만 읽어 점수 확장 가설을 시험했다. 이것은 **ANNCUR의 학습 모델·검색 알고리즘 전체 재현이 아니며, 단순 CUR와 안정화 변형의 탐색 실험**이다. 새 판단 모델이나 API를 호출하지 않았고 추론 속도·새 요금도 측정하지 않았다.

### 7.1 입력과 분할

- 점수 출처: `results/length_20261004T105521_c4d2d4a4/retrievals.jsonl`의 목표 720 조건만 사용. 40개 개발 질문 × 100개 그룹의 Noul 확률 행렬.
- 정답 출처: 같은 실행의 `development_labels.json`. 그룹→원문 연결은 `data/parallel_groups/b50942af2b35381ae4fd3a67/groups.json`.
- 질문을 `(task, question_id)`로 정렬한 뒤 NumPy `default_rng(20261004)`로 task별 인덱스를 섞는다. 각 task의 처음 14개를 기준 질문, 나머지 6개를 검증 질문으로 사용한다. 총 기준 질문 28개, 검증 질문 12개.
- 기준 행의 실제 모든 그룹 점수로 \(H\in\mathbb R^{28\times100}\)를 구성한다. 검증 질문에서는 선택한 기준 그룹 \(J\)의 실제 점수만 근사 입력으로 사용한다. 나머지 검증 점수는 teacher 비교에만 사용한다.
- 선택 그룹 수는 기존과 동일한 5개. 점수 동점은 그룹 ID 오름차순. 선택한 그룹의 모든 원문 ID를 합쳐 정답 근거 ID 집합을 포함하는지 평가한다. **이는 Macro 완전 확보이며 최종 원문 선택·답변 EM이 아니다.**

검증 12문항의 전체 100그룹 실제 판단은 **11/12 Macro 완전 확보**다.

### 7.2 두 가지 근사 결과

첫 변형은 위 RNG에서 이어서 그룹 인덱스 100개를 섞어 기준 그룹 4·8·16·24·32개를 선택한다. \(\widehat S=V_{:,J}\operatorname{pinv}(H_{:,J})H\), `rcond=1e-6`을 사용한다.

첫 결과의 수치 불안정성을 확인한 뒤, 개발 탐색의 두 번째 변형으로 기준 행에서만 residual column norm이 큰 그룹을 순차 선택하는 pivoted modified Gram-Schmidt를 사용하고 ridge를 0.1로 고정했다.

\[
A_\lambda=(H_{:,J}^{\mathsf T}H_{:,J}+0.1I)^{-1}H_{:,J}^{\mathsf T}H,
\qquad\widehat S=V_{:,J}A_\lambda.
\]

| 실제 판단한 기준 그룹 수 | 무작위 기준 + 단순 pinv: Macro 완전 확보 | 기준 행에서 선택 + ridge: Macro 완전 확보 | ridge 변형의 teacher top-5 겹침 평균 |
|---|---:|---:|---:|
| 4 | 0/12 | 1/12 | 11.7% |
| 8 | 1/12 | 1/12 | 11.7% |
| 16 | 1/12 | 2/12 | 28.3% |
| 24 | 1/12 | 3/12 | 36.7% |
| 32 | 0/12 | 3/12 | 40.0% |
| 100그룹 모두 실제 판단 | 11/12 | 11/12 | 100% |

단순 pinv는 추정 점수가 0~1 밖으로 나가고 오차가 크게 증폭됐다. 안정화 변형에서는 수치 오차를 줄였지만 필요한 그룹 누락이 여전히 많았다. 기준 행의 최적 rank-8 근사도 상대 Frobenius 잔차가 약 0.549, rank-16은 약 0.286이었다. 이를 모든 Jev 점수의 일반적 rank 특성으로 해석하지 않는다.

**현재 28개 기준 질문과 원래 Noul 확률을 단순 확장하는 방법은 품질 유지에 실패했다.** 기준 질문 수·다양성, 기준 그룹 선택, 확률 변환, 모델의 표현 구조를 바꾸면 결과가 달라질 수 있으므로 ANNCUR 자체의 불가능성 증거는 아니다. 반대로 논문이 있으니 작은 기준 집합으로 근거를 보존할 수 있다고 전제해서도 안 된다. 이 작은 개발 결과 때문에 현재는 질문 전용 로컬 라우터 쪽을 우선 검토한다.

원본 점수 행렬은 이미 비용을 지불한 기록이지만, 실제 새 질문에서도 기준 그룹마다 Jev 입력 요금은 발생한다. Macro의 평균 판단당 약 748토큰을 그대로 가정하면 기준 그룹 8개만 평가해도 약 5,982토큰이며, §6의 생성 요금이 0인 가상 한도 약 2,414토큰보다 크다. 실제 배치 구성에 따라 반복 지시문 길이는 달라질 수 있지만, **근사 성공만으로 전체 API 비용 우위가 성립하지는 않는다.** Micro 비용도 따로 남는다.

## 8. 우선 연구할 구조

주 연구 가설은 아래와 같이 구체화할 수 있다. 이것은 구현 완료나 성공 판정이 아니라 문헌·비용·개발 재생에 근거한 설계 제안이다.

```text
사전 준비
원문·위치 저장 + 그룹 연결
→ 원문에서 학습 질문·관련/비관련 사례 준비
→ 로컬 다중 라벨 라우터와 원문 판단기 학습

온라인
질문 → 질문 전용 로컬 라우터 → 복수 그룹의 원문 후보
→ 로컬 원문 판단 → 필요한 근거·원문 위치 → 공통 LLM
                ↘ 실패 위험이 큰 경우만 제한된 Jev 확인
```

핵심은 그룹의 의미를 매번 API로 읽히지 않고 학습된 로컬 라우터로 재사용하며, Micro의 원문 판단도 로컬에 옮기는 것이다. 사람이 만든 고정 키워드 규칙으로만 분기하는 구조나 RetroMAE 후보를 그대로 받는 구조와는 다르다. 모델이 질문과 자료를 의미적으로 판단하되 저장·참조·예산 관리·집계는 코드가 맡는다.

개발 목표는 예를 들어 다음 제약 문제로 적을 수 있다.

\[
\min_\theta\left(
\mathbb E[C_{\mathrm{total}}(q;\theta)],\;
T_{95}(\theta)
\right)
\quad\mathrm{s.t.}\quad
R_{\mathrm{complete}}(\theta)\ge R_0,\quad
\operatorname{EM}(\theta)\ge \operatorname{EM}_B+\delta.
\]

\(\theta\)는 학생 모델·선택 그룹 수 정책·원문 판단 예산·fallback 정책·근거 전달 규약이다. \(R_0\)와 의미 있는 개선 폭 \(\delta\)는 최종 평가 전에 고정한다. 한 질문의 일부만 뒷받침하는 근거도 살리는 학습 라벨을 사용하고, 확률이 높다는 이유만으로 충분성이나 근거 완전 확보를 보장한다고 취급하지 않는다.

### 8.1 생성기 토큰 절약은 별도 축으로 확인한다

현재 A/B/C의 공통 생성기 입력은 약 880토큰으로 비슷하다. 자료 5개를 유지하면서 답에 필요한 원문 문장·표 행만 추출하는 방법은 검토할 수 있다. [LLMLingua-2, ACL Findings 2024](https://aclanthology.org/2024.findings-acl.57/)는 큰 모델의 압축 판단을 작은 encoder의 토큰 보존·삭제 분류기로 옮긴 연구다. 원문의 다른 작업에서 얻은 절감률을 우리의 짧은 입력에 대입하지 않는다.

압축한다면 원문 위치를 유지하고 고유명사·숫자·부정·조건·복수 근거를 보존하는지 확인한다. 압축기 자체의 시간과 로컬 비용까지 넣어 실익을 평가한다. 같은 원문 개수를 전달했다는 조건만으로 같은 정보가 전달됐다고 보장할 수 없다.

### 8.2 이 연구가 새로워지려면

Jev + 트리, 질문→문서 ID 학습, 판단 모델 증류, 문서 캐시는 각각 선행 사례가 있다. 이 구성요소들을 붙였다는 주장보다 **복수 근거를 놓치지 않으면서 온라인 의미 판단을 얼마나 적게 수행할 수 있는지**, **모델·자료 규모·갱신 빈도에 따라 최적 예산과 손익분기가 어떻게 바뀌는지**에 기여를 두는 편이 명확하다.

고정 A/B보다 나은 결과와 모든 RAG보다 나은 결과도 구분한다. 후자를 주장하려면 더 강한 검색·재정렬 설정과 다른 데이터·규모까지 비교해야 한다. 우선은 기존 A/B가 동일 질문·GPU·공통 생성기에서 만족하는 품질을 넘는 정책을 개발하고, 새 고정 평가에서 답변·근거·시간·비용의 차이와 불확실성을 확인한다.
